# ESP-Streamer Core V2 (development)

[Core guide](README-RADIO.md) | [Project overview](../README.md)

This is a separate build profile on the `v2` development branch, not an
automatic replacement for the installed V1 firmware. Do not flash it before
rewiring and hardware validation. No on-device V2 validation has been performed.

## Implemented scope

- Two independent 3.3 V UART control links: 115200 baud, 8 data bits, no parity,
  1 stop bit, no hardware flow control. Connect common ground and cross TX/RX.
- Shared radio selection logic for both UARTs and the existing HTTP API.
- Live full-status snapshots every two seconds on each link, even when the
  source is AirPlay or the radio is offline. A `status` request gets an
  immediate snapshot. Status includes source, playing/buffering state, metadata,
  format, reported bitrate, errors and output diagnostics.
- Ordinary changes during AirPlay return conflict without saving the URL or
  changing the selected station. Explicit override closes existing RTSP clients,
  bypasses the paused-session reconnect grace period, waits up to five seconds
  for cleanup, then selects radio. New RTSP connections are blocked during the
  operation and allowed again afterward; this is not a permanent AirPlay lockout.
- The existing webpage supports V1 and V2. For V2 it disables ordinary radio
  controls during AirPlay unless the explicit disconnect checkbox is enabled.
- GPIO21 optical S/PDIF and GPIO47 mirrored coax data use the same encoded
  signal and hardware clock. GPIO47 is logic-level data for the external driver,
  **not** a direct electrical coax output.
- DIT4096 native-rate PCM on I2S1, with ESP-generated MCLK/BCK/LRCK,
  reset sequencing, a bounded nonblocking producer queue and output diagnostics.

### Not implemented/enabled yet

Sony CXD2560M PCM and ATT/SHIFT/LATCH control remain disabled.
The API reports `sony_pcm_enabled:false`; DIT PCM is enabled in V2 only.

The DAR-1000ES service manual has been supplied for further Sony investigation;
the CXD2564AM datasheet is not proof of CXD2560M timing or voltage compatibility.
Sony external master-clock frequency, input timing and level compatibility
still need to be established before enabling its output.

The ESP32-S3 has two I2S peripherals, now allocated to software-encoded S/PDIF
and DIT PCM. Sony cannot be added as another independent I2S clock domain.
Do not enable incompatible formats or an externally clocked Sony input by
merely duplicating the DIT pins.

## Pin mapping

These are **ESP GPIO numbers**, not the schematic's header position numbers.

| Function | Header position | GPIO | State |
|---|---|---|---|
| ESP_Controller: radio RX | 4 | 4 | Enabled |
| ESP_Controller: radio TX | 5 | 5 | Enabled |
| ESP_DISPLAY: radio TX | 6 | 6 | Enabled |
| ESP_DISPLAY: radio RX | 7 | 7 | Enabled |
| Optical S/PDIF | 40 | 21 | Enabled; requires moving the V1 GPIO14 wire |
| Coax data | 39 | 47 | Enabled; external driver required |
| Sony ATT / SHIFT / LATCH | 15 / 16 / 17 | 9 / 10 / 11 | Reserved, not driven |
| Sony LRCK / DATA / BCK | 18 / 19 / 20 | 12 / 13 / 14 | Reserved, not driven |
| DIT MCLK / BCK | 31 / 32 | 39 / 38 | Enabled |
| DIT LRCK / DATA / RST | **8 / 9 / 10** | **15 / 16 / 17** | Enabled; approved rewire required |

Do not wire DIT signals to GPIO35/36/37 as in the original drawing; these are
reserved by octal memory on the ESP32-S3 N16R8. Preserve the GPIO48 playback LED.
Verify the board's actual module/pin labels before connecting anything.

## DIT4096 native PCM

The following are **DIT IC pin numbers**, not ESP GPIOs:

- Confirmed connected to 3.3 V: MODE28, EMPH23, BLSM24, COPY2, L3,
  CLK0(5), VIO7 and FMT0(9).
- Required LOW straps shown in the schematic: M/S14, FMT1(10), CLK1(4).
  This selects hardware configuration, slave operation, 24-bit Philips I2S
  and 256-times-sample-rate MCLK. EMPH HIGH means no pre-emphasis.
- With CSS1 LOW as drawn, COPY and L both HIGH select professional AES3
  channel status, not consumer S/PDIF status. Verify downstream compatibility.
  BLSM HIGH makes BLS25 an output; do not externally drive it.
- VDD19 uses 5 V; VIO7 uses 3.3 V. Connect the documented grounds and
  verify all remaining status/user/validity inputs against the datasheet.
  In particular, do not leave V26 floating: LOW marks audio valid.
  The confirmed HIGH list alone does not establish those remaining connections.
- GPIO17 drives active-LOW reset; ESP supplies all three audio clocks.
  No separate oscillator is needed.

| Source / LRCK | MCLK (256fs) | BCK (64fs) |
|---|---|---|
| 32 kHz | 8.192 MHz | 2.048 MHz |
| 44.1 kHz | 11.2896 MHz | 2.8224 MHz |
| 48 kHz | 12.288 MHz | 3.072 MHz |

These are nominal clock frequencies; physical accuracy needs measurement.
The current decoder supports these rates, not the DIT chip's full 96 kHz range.
PCM is tapped **before** the optical resampler. MP3/AAC/ALAC still have to
decode to PCM, but this path adds no lossy codec or sample-rate conversion.
The existing decoded signal is 16-bit stereo, packed into a 24-bit I2S payload
with eight zero low bits and 32-bit slots. Padding does not create 24-bit
precision. AirPlay volume ramping and the existing receiver timing corrections
still apply; this is not an end-to-end bit-perfect guarantee.
Optical/coax remain 48 kHz and keep their existing resampling/volume path.

Reset stays asserted while the native DMA ring is filled (3072 frames,
64-96 ms). Source changes/flush/stop invalidate queued blocks; the worker
mutes and restarts with the new rate. Producers never wait on the DIT queue,
so a slow DIT output cannot block the optical task. Queue overflow and DMA
write errors log/count a reset. A lack of new PCM for over 100 ms also
mutes/rebuffers; output DMA auto-clears consumed buffers to silence.
Direct writes outside the normal playback task use the physical 48 kHz format.

The native and optical outputs have independent clocks and buffering. Their
latencies are not synchronized; the existing AirPlay timing reference remains
the optical output. Fractional clock error, source/network stalls or sustained
clock drift can cause DIT silence/rebuffering. There is no independent DIT
clock servo or adaptive resampling. Do not interpret a successful build as
proof of indefinite glitch-free simultaneous output.

HTTP and both UART status snapshots include `dit_pcm_enabled` and a `dit`
object: `running`, `sample_rate`, `mclk_hz`, `bclk_hz`, `pcm_bits` (16),
`container_bits` (24), `slot_bits` (32), `write_errors`, `queue_overflows`,
`starvation_resets`, `frames_submitted`. Rates/clocks are zero while muted.
Counters are cumulative; submitted frames are DMA writes/preloads, not proof
of audible playback. Starvation resets detect input gaps, not every DMA
underrun. The webpage shows native format/clocks and error/reset counters.

## UART protocol v2

Each message is one UTF-8 JSON object terminated by LF (`\n`); CRLF is accepted.
Maximum inbound line length: 1023 bytes excluding LF, including an optional CR.
An optional string `id` of up to 64 bytes is echoed in command responses.
Send one command at a time per link and wait for its response. Accept interleaved
unsolicited status messages. Do not send firmware debug text to these UARTs.

```json
{"id":"1","cmd":"status"}
{"id":"2","cmd":"set_stream","url":"https://example.org/live.mp3"}
{"id":"3","cmd":"set_station","station":0}
{"id":"4","cmd":"set_stream","url":"https://example.org/live.mp3","override":true}
```

Station IDs remain 0=NPO, 1=BNR, 2=538, 3=SLAM, 4=custom. Custom selection
requires a URL. Both controllers have equal authority; commands are serialized.
There is no controller priority, volume command or automatic controller reboot.

Successful response (status abbreviated here, never abbreviated on the wire):

```json
{"type":"response","protocol_version":2,"link":"ESP_Controller","id":"2","code":200,"ok":true,"message":"Selection accepted; playback may still be buffering","status":{"source":"Radio"}}
```

AirPlay conflict:

```json
{"type":"response","protocol_version":2,"link":"ESP_DISPLAY","id":"2","code":409,"ok":false,"message":"AirPlay owns playback; use override:true to disconnect it"}
```

Unsolicited event:

```json
{"type":"status","protocol_version":2,"link":"ESP_DISPLAY","status":{"source":"AirPlay"}}
```

The complete `status` object is the same schema as `GET /api/radio`.
Use `source` to distinguish radio from AirPlay; `airplay.playing` distinguishes
paused AirPlay from playing. `now_playing` includes title, artist, album,
stream name, codec, sample rate, channels, reported `bitrate_kbps`, configured
radio URL and output format. Missing metadata is empty, not fabricated.
Source bit depth is reported only when known; radio source bit depth is `0`
(unknown), while output PCM is 16-bit. Radio titles can lead buffered audio.
The top-level `frames_played` counts radio only; use AirPlay `chunks_decoded`
for its progress. Counters are diagnostics, not a subjective quality score.

Error codes: 400 malformed/invalid input, 409 AirPlay owns playback, 500 memory
or persistence failure, 503 busy controller or AirPlay cleanup timeout.
Concurrent commands wait up to 250 ms for the control lock before returning
busy; retry after the previous command finishes. A 200 confirms command
acceptance, not successful stream playback. Inspect subsequent status/errors.
Oversized/corrupt lines are discarded through the next newline. UART framing,
parity, break and receive-buffer errors are reported explicitly and require
newline resynchronization. Transport buffers are bounded; command flooding can
cause receive overflow. Periodic events resume after command handling.

## HTTP API

Keep using `GET /api/radio` and `POST /api/radio`:

```json
{"url":"https://example.org/live.mp3"}
{"station":2}
{"station":0,"override":true}
```

HTTP responses use the same 200/400/409/500/503 meanings. The endpoint remains
unauthenticated and local-network-only. Both API and UART reject regular
selections during AirPlay; this intentionally differs from V1's queued changes.
The existing HACS integration will report HTTP 409 for such a selection; it
cannot force-disconnect AirPlay and does not silently claim success.

## Build and validation

From the repository root, initialize submodules, then:

```powershell
Set-Location firmware
pio run -e radio-s3-v2
pio run -e radio-s3-v2 -t buildfs
```

V1 remains available through `radio-s3`, retaining GPIO14 and queued selections.
V2 uses the same partition layout/NVS as V1, but has different wiring and policy.
Do not flash a V2 application with the V1 optical wiring unchanged.
The device webpage needs its own update; application OTA does not update SPIFFS.

Before hardware approval: check both UARTs with independent controllers; exercise
valid/invalid/fragmented and oversized requests, concurrent changes, live song
updates, AirPlay conflict without URL persistence, override during play/pause,
timeout reporting, later AirPlay reconnect, radio fallback and optical/coax
waveforms. Verify continued playback under status traffic and controller floods.
Host parser tests and a successful build do not verify these hardware behaviors.

Host regression tests:

```text
cc -Wall -Wextra -Werror -I <cJSON-include-directory> tests/test_radio_control.c main/audio/radio_command.c main/audio/radio_line.c <cJSON-source-directory>/cJSON.c -o test_radio_control
cc -Wall -Wextra -Werror tests/test_dit4096_format.c -o test_dit4096_format
cc -Wall -Wextra -Werror tests/test_led_playback.c -o test_led_playback
node tests/test_radio_web.cjs
```

Run the resulting C test executable. It exercises the actual command parser and
line framer (including fragmentation, CRLF, oversized lines and resynchronization).
The Node test executes the actual webpage script with a small DOM/HTTP fixture;
it checks V1 compatibility and V2 override/payload behavior, not a browser layout
or a real AirPlay session. The existing ICY and Home Assistant regression tests
remain applicable.
The DIT format test checks every signed 16-bit sample's DMA packing and all
supported clock ratios, including rejection of unsupported source rates.
The LED test checks idle/radio indications, one-second AirPlay blink edges,
paused connections, source changes and blink restart on reconnection.

DIT hardware acceptance additionally requires verifying reset, MCLK/BCK/LRCK
and I2S alignment at all three rates with a logic analyzer, downstream lock and
correct channel/level playback, mute/pause/seek/source/rate changes, AirPlay
volume, and a long simultaneous-output soak test watching the DIT counters.
